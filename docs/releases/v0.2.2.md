# XXL-JOB 0.2.2

## Store-Facing Release Notes

0.2.2 is the first Store update since 0.1.1. It exposes 13 lifecycle-bound MCP tools over the existing XXL-JOB Admin API: read (xxljob_info, xxljob_groups, xxljob_jobs, xxljob_jobs_by_group, xxljob_logs, xxljob_log_content), write (xxljob_start, xxljob_stop) and full-access administration (xxljob_trigger, xxljob_save_job, xxljob_remove_job, xxljob_save_group, xxljob_remove_group), keeping the existing confirmation and read-only guards; manifest permissions remain empty and upgrading grants no access. It also corrects the author release metadata so DBX Store can import the release, and removes the unsupported mcpTools field. UI behavior is unchanged. A matching updated DBX Desktop and standalone MCP are required.

## Why A New Version

Neither 0.2.0 nor 0.2.1 entered the Store. Describing only the 0.2.1 metadata
repair omitted the lifecycle-bound MCP bridge that users upgrading from Store
0.1.1 will actually receive. The author release must use the Store-importable
top-level `plugin` identity plus `artifacts` envelope rather than a flat catalog
candidate; unsupported `mcpTools` listing metadata must remain absent. MCP
declarations stay in the unchanged packaged manifest.

0.2.2 is a new immutable release for the maintainer-review response and clean CI
provenance. Preserve 0.2.0/0.2.1 tags, assets, notes and receipts; none establishes
0.2.2 verification. Source is pinned to
[`v0.2.2`](https://github.com/caichangqing1120/dbx-plugin-xxl-job/tree/v0.2.2).

## Required CI And Provenance Gates

Use clean CI through the official reusable workflow pinned at
`417c1bfc28ea8669dfbc2e1525f54e3b68285b1c`. Its caller sets
`install-plugin-cli: false` to avoid rewriting the backend module and preserves
the existing `replace ... => ./sdk` relationship. Go 1.26.3 builds the sidecar
directly through the provenance-aware helper:

```sh
RELEASE_TAG=v0.2.2 DBX_PLUGIN_TARGET=<target> python3 scripts/package-ci.py
```

For each of the six supported targets, the helper emits
`dist/<id>-<version>-<target>.dbxp`, `.artifact.json` and `.provenance.json`.
Full VCS provenance verification is mandatory: inspect the packaged executable's
`go version -m` build information, require `vcs.revision` to equal the commit
resolved by `v0.2.2`, require `vcs.modified=false`, and retain the complete build
information and provenance record. Missing or mismatched provenance must fail
packaging, even if initialize reports 0.2.2. Check packaged identity/version,
target architecture and SHA256/size against emitted metadata and final release
inputs; import the unmodified author envelope through the actual Store importer
and validate its generated catalog candidate.

Fresh 0.2.2 CI execution, downloaded-byte/provenance verification, immutable author
publication and Store review/signing are pending delivery gates. These notes do
not claim any of those results. Historical or local packages cannot substitute
for clean CI output.

## Unchanged Safety And Acceptance Boundaries

All 13 exact MCP declarations retain six `read`, two `write` and five `full`
classifications. Existing lifecycle identity, confirmation and read-only guards,
API profiles, plugin ID/publisher, empty manifest permissions and UI remain
unchanged. Installing or upgrading grants no access. Explicit enablement and
connection/tool authorization require matching updated DBX Desktop and standalone
MCP; the existing engine floor alone does not demonstrate new protocol support.

No new Desktop installation, live XXL-JOB Admin acceptance, task execution,
production-service call or official Store signing is established by the
metadata/docs update. Fixture tests, builds and Store validation are separate
evidence and must not be described as live scheduling acceptance.
